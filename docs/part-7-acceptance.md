# 第七部分：AI 调用限制与恢复

## 已实现

- 默认关闭新模型调用。服务端同时有 `AI_ENABLED=true`、`OPENAI_API_KEY` 和明确的 `OPENAI_MODEL`，且当前用户确认本次发送和费用后，才可以开始新调用。
- 每人每天最多 5 个预约，整个应用最多 20 个；按 UTC 计日、跨项目共用，同时最多 1 个有效运行预约。
- 单次请求体最多 16 KiB、最多 1,200 输出 tokens，外部 HTTP 等待最多 45 秒。只发送汇总指标、主题计数和建议 ID，不发送原文、标题、账号或文件。
- 一次预约对应一次应用层外部 HTTP 尝试，没有自动退避重试。内置请求 ID 用于关联排查，不当作服务商幂等保证。
- 行动建议先经过结构/ID/长度等校验，再保存为检查点。报告保存失败后保留同一请求编号恢复，使用已有检查点，不重新调用模型。
- 已知失败与网络/中断导致的结果未确认分开记录；两者都不会对同一请求自动重发。统计与规则建议可保存为回退结果，不冒充 AI 成功。
- 失败与未确认的预约计入当日次数，不自动退款或重置。删除项目不删除计数，避免以项目重建绕过上限。
- 页面显示策略、本人用量、UTC 重置时间和刷新入口。演示只显示默认策略，完全不查询真实用量或调用模型。
- 重新运行分析会取消上一次勾选，下一次新调用需再次确认；同一请求的恢复保留请求编号。关闭新调用开关时，只要模型与输入保持一致，已有检查点仍可恢复。
- 报告记录建议生成状态与模型；数字、证据、统计与评论初筛仍来自确定性引擎。

## 失败时如何处理

| 情况 | 行为 |
| --- | --- |
| 正在处理，同一请求再次提交 | 返回进行中，稍后用同一请求恢复；不发起第二次模型请求 |
| 个人/应用次数用完或其他预约占用 | 返回限制提示；可等待或关闭 AI 保存规则报告 |
| 模型返回但报告保存失败 | 使用已有检查点恢复，不重新调用模型 |
| 网络中断、超时或实例终止 | 不知道服务商是否已接收/计费，同一请求不自动重发 |
| 检查点写入也失败 | 保留运行预约，等待恢复；120 秒租约到期后转未确认，不重新获取调用资格 |
| 输入、模型或操作者改变 | 不默默复用旧请求，需重新核对并明确创建新请求 |
| 没有可以生成行动建议的证据 | 不预约、不请求模型，也不标记 AI 生成 |

有效预约并发限制是应用层租约，不保证中断后服务商内部任务已物理停止。次数限制不是金额硬预算，也不覆盖其他应用使用同一服务商密钥；真正付费前仍需核对模型价格、服务商预算配置及实际账单。

页面明确区分「保存待确认」与「已保存分析」，显示本次请求编号。仅在本标签页的 sessionStorage 保存当前用户/项目的最近一次未确认请求编号、AI 意图和筛选；刷新后恢复这些状态，但必须手动点击，不自动调用。成功后清除记录；记录最长有效 7 天，关闭标签页清除，跨设备/关闭后恢复仍未实现。它不包含原始评论、标注或密钥；筛选可能含项目主题文字，需按项目数据范围对待。新的请求会替换同项目的旧恢复记录。

## 内部控制与权限

新增 `private.ai_call_policy` 和 `private.ai_call_requests`，两表有 RLS、无普通用户/anon/service_role 直接表权限。global 计数需要看到其他工作空间的预约总数，因此以固定 search_path、明确 auth.uid 和项目编辑权限检查的窄 SECURITY DEFINER 函数维护账本。公共 RPC 包装为 SECURITY INVOKER。
任何业务读取/保存仍使用调用用户 JWT 和原有 RLS，不新增高权限服务密钥。操作只返回当前用户用量和其本人请求的状态，其他用户账本不可读取。
预约采用事务级全局 advisory lock；服务端随机临时令牌绑定检查点写入，令牌不返回浏览器。源数据、筛选、模型、处理版本的 SHA-256 绑定请求，采集时间的变化不触发新的调用。
账本不随项目删除级联清理，当前无自动清理；没有原始评论或文件正文，仍可能保留项目/用户标识和生成的行动文本。完整个人数据删除治理仍是待办。
两张 private 表的「RLS 无策略」提示为有意默认拒绝，非新增业务数据访问漏洞。调用控制记录不是服务商签名的支付/作者审计证明。
