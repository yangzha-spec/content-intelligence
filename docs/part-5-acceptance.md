# 第五部分：原文件保留与清理

## 无需登录的体验

打开示例项目的「导入与入库」，在导入历史下方点击「查看清理影响示例」。演示展示 Posts / Metrics / Comments 三类文件与保留范围，没有云端原文件，也不调用删除接口。

## 真实项目操作

1. 打开真实项目的导入历史，选择一个批次。所有成员能看到保留状态和来源，只有空间所有者有清理入口。
2. 查看本批文件清单、大小及永久删除的影响；需要原文件时先自行下载。
3. 输入「清理原文件」并点击本批确认。没有批量清空、自动过期或定时清理。
4. 原文件在 Storage API 删除、数据库确认无文件后才显示已清理。中断保留「清理中」，刷新后由所有者确认继续。
5. 来源、SHA-256、映射和入库数量保留，并记录清理人、开始与完成时间。成功导入不重复新增，已入库内容与历史报告保持可读。

默认持续保留，由团队按实际授权/合同决定何时手动处理。开始清理后不可恢复旧批次，旧批次不能继续补传、复核或入库；未入库的数据需建立新批次重新上传。
清理只移除原始文件，不是完整个人数据删除。已入库评论、分析输入快照、报告及本地下载副本需要另行处理。

## 权限与一致性

- 所有新 RPC 与辅助函数为 SECURITY INVOKER；不新增 service_role 授权、服务密钥或后台定时任务。
- Storage 删除策略只允许所有者清理状态为 deleting 的批次清单路径；编辑者、viewer、非成员和匿名用户不能清理。
- SQL 只读 Storage 元数据以核对完成，不执行 Storage DELETE；实际字节由用户 JWT 下的 `remove` API 删除。
- retained → deleting → deleted 单向变化；服务器记录时间和操作者，不能直接跳过或回退。
- 上传策略持有批次共享锁，清理/入库使用一致的项目与批次锁；清理开始后禁止写入和补传，避免文件迟到。
- 完成之前检查同一批次目录是否仍有对象；残留或失败不能标记成功。重复完成返回原状态。
- 未清理含文件清单的批次前，禁止删除相应项目、空间和批次；仍无项目/空间删除页面。
- 成功批次继续按请求指纹去重；清理中的失败/未完成批次释放指纹，新上传使用新批次，旧来源保留。

## 已完成验证（2026-11-04）

- 自动测试共 102 项通过，包括真实 PostgreSQL 引擎中的状态、owner/editor/viewer/非成员权限、父实体删除保护、完成核对、入库保留、失败重试、不可回退与旧批次禁止写入。
- Supabase JS 客户端模拟 HTTP 验证确认文字、JWT、只删除服务器授权路径、Storage 失败不完成、部分清理不误报、重复完成不再删除。
- 云端 `06_original_lifecycle_smoke.sql` 验证所有者生命周期、其他角色拒绝、来源/入库数据保留与项目删除保护；全部测试用户和业务数据回滚，没有创建/删除任何 Storage 对象。
- 类型检查与生产构建通过。浏览器验证清理影响展开与只读演示，390 像素窄屏页面无横向溢出。
- 已更新 `import-batch` 服务，清理中的旧批次在下载原文件之前拒绝复核和入库。
